# KBEngine 性能压测使用文档

本文档说明如何使用当前项目内置的性能压测工具，对 KBEngine 服务端进行 Bots 压测、KCP/TCP 对照、探针开关 A/B 测试，以及如何读取报告指标。

压测入口位于：

```text
D:\KBELAB\kbengine\kbengine1x\kbe\src\tests\performance
```

默认结果输出目录位于：

```text
D:\KBELAB\kbengine\kbengine1x\kbe\src\out\performance-runs
```

## 一、压测目标

当前压测框架主要用于验证以下内容：

- 服务端在指定 Bots 数量下是否能完成登录、进入 Play 状态和 Witness 建立。
- BaseApp、CellApp、Bots、控制器自身的 CPU、内存、线程数、句柄数等进程指标。
- BaseApp / CellApp 的 Tick 延迟、Python 调用延迟、onTimer 延迟、客户端输入处理、AOI/Witness 队列和 KCP 调度状态。
- KCP 与 TCP 游戏链路的对照表现。
- 性能探针开启与关闭时的成本差异。
- 日志错误、协议错误、客户端掉线、Entity 异常销毁等质量门。

注意：报告里的 `request latency` 默认指 Watcher 控制面请求往返时间，不等同于真实游戏 RPC 延迟。真实 Python 层到底层的业务 P50/P95/P99/P99.9 需要依赖业务侧关联请求/响应或已有 cprofile / scriptStages 指标综合判断。

## 二、环境准备

### 1. 编译 Release 服务端

压测必须优先使用 Release。Debug 会明显放大 CPU、内存、日志和断言成本，不能作为正式性能基线。

推荐在 `Developer PowerShell for VS 2022` 中运行：

```powershell
cd D:\KBELAB\kbengine\kbengine1x
.\install\install_windows.ps1 -Configuration Release
```

如果只需要使用已有 CMake 构建目录，也可以直接构建：

```powershell
cd D:\KBELAB\kbengine\kbengine1x\kbe\src
cmake --build --preset windows-ninja-tests-release
```

服务端程序会部署到：

```text
D:\KBELAB\kbengine\kbengine1x\kbe\bin\server
```

压测 runner 默认也会从该目录启动 `machine.exe`、`baseapp.exe`、`cellapp.exe`、`bots.exe` 等组件。

### 2. 数据库

本机 MySQL 可使用以下账号：

```text
root/root
kbe/kbe
```

运行前请确认 MySQL 已启动。数据库未启动时，常见现象是 `dbmgr` 或其他组件发现失败、连接数据库失败、集群 readiness 超时。

### 3. 业务资产

正式压测资产路径示例：

```text
D:\KBELAB\KBEProject\kbengine_stresstest\mmorpg\server_assets
```

该目录必须包含：

```text
res/server/kbengine.xml
scripts/entities.xml
```

压测 runner 不直接修改源资产，而是复制并生成本轮隔离配置覆盖层：

```text
<run目录>\config-overlay\res\server\kbengine.xml
```

因此压测参数不会污染业务工程原始配置。

## 三、标准压测命令

所有命令建议从仓库根目录执行：

```powershell

```

### 1. 4000 Bots 快速验证，关闭探针

用于确认基础链路、观察纯运行成本。

  --bots-no-tcp-fallback `
  --server-ready-timeout 300 `
  --workload-ready-timeout 300

## 四、关键参数说明

| 参数 | 作用 | 建议 |
| --- | --- | --- |
| `--scenario` | 选择压测场景 JSON | 正式 KCP 用 `gameplay_10000.json` |
| `--assets-root` | 业务资产目录 | 使用 mmorpg 的 `server_assets` |
| `--tools-root` | Watcher 查询工具目录 | 固定为 `kbe\tools\server` |
| `--start-cluster` | 由 runner 启动并托管服务端集群 | 标准压测必须开启 |
| `--baseapp-count` | 启动 BaseApp 数量 | 本机高并发建议 9 到 10 个起步 |
| `--cellapp-count` | 启动 CellApp 数量 | AOI 压力大时建议 10 个起步 |
| `--bots` | 机器人总数 | 快速验证 4000，正式验证 10000 |
| `--bots-processes` | Bots 进程数 | 4000 可用 8，10000 可用 40 |
| `--bots-transport` | BaseApp 游戏连接传输协议 | `kcp` 或 `tcp` |
| `--bots-no-tcp-fallback` | 禁止 KCP 失败后回退 TCP | 纯 KCP 压测必须加 |
| `--server-ready-timeout` | 等待 BaseAppMgr / CellAppMgr ready 的秒数 | Space 多时建议 300 秒 |
| `--workload-ready-timeout` | 等待 Bots 全部进入目标状态的秒数 | 大量 Bots 建议 300 秒 |
| `--duration` | 覆盖场景持续时间 | 临时短测可设 60 |
| `--output-root` | 自定义结果目录 | 默认即可 |

## 六、压测流程

### 1. 清理旧服务端进程

如果之前有残留进程，需要先关闭。可以用任务管理器，也可以用 PowerShell：

```powershell
Get-Process machine,logger,interfaces,dbmgr,baseappmgr,cellappmgr,baseapp,cellapp,loginapp,bots -ErrorAction SilentlyContinue |
  Stop-Process -Force
```

### 2. 确认数据库启动

```powershell
mysql -uroot -proot -e "select 1;"
```

或者：

```powershell
mysql -ukbe -pkbe -e "select 1;"
```

### 3. 编译 Release

```powershell
cd D:\KBELAB\kbengine\kbengine1x
.\install\install_windows.ps1 -Configuration Release
```

### 4. 运行压测

选择第三节中的命令运行。

Runner 会自动完成：

- 生成隔离配置 overlay。
- 启动 Machine、Logger、Interfaces、DbMgr、BaseAppMgr、CellAppMgr、BaseApp、CellApp、LoginApp。
- 等待 BaseAppMgr / CellAppMgr 的 `root/readiness` 达到可登录状态。
- 启动多个 Bots 进程。
- 等待 Bots 达到 readiness。
- 进入稳态采样窗口。
- 写入 `raw.jsonl`、`summary.json`、`report.md`。
- 尝试优雅停止本轮拥有的进程。

### 5. 查看结果

压测结束时，终端会输出本轮 `run_id` 和 `output`。例如：

```text
D:\KBELAB\kbengine\kbengine1x\kbe\src\out\performance-runs\gameplay-10000-20260810-010203-abcdef12
```

重点查看：

```text
report.md
summary.json
raw.jsonl
logs\
```

`report.md` 适合人工阅读，`summary.json` 适合提取发布指标，`raw.jsonl` 适合二次分析。

## 七、重点指标解释

### 1. 质量状态

`summary.json` 中：

```json
{
  "quality": {
    "status": "PASS"
  }
}
```

`PASS` 表示当前质量门没有发现阻断项。`FAIL` 不一定代表服务端完全不可用，但说明本轮不能作为正式发布数据，需要看 `quality.blockers`。

### 2. Readiness

正式 gameplay 场景通常要求：

- `root/bots/performance/clientsTotal == bots`
- `root/bots/performance/clientsKcp == bots`，KCP 压测时
- `root/bots/performance/clientsTcp == bots`，TCP 压测时
- `root/bots/performance/clientsStatePlay == bots`
- `root/bots/performance/clientsDestroyed == 0`
- `root/bots/performance/networkErrors == 0`
- `root/witness/active` 达到预期数量

如果 readiness 没达到，说明压测未进入完整稳态，不能作为正式吞吐结论。

### 3. CPU

进程 CPU 采样会按整机逻辑处理器数归一化。需要同时看：

- 单个 BaseApp / CellApp 是否接近单核瓶颈。
- 总 CPU 是否还有余量。
- 是否存在某几个 CellApp 明显高于其他 CellApp，说明 Space / AOI / Witness 分配不均。
- Bots 进程是否抢占了服务端 CPU。

游戏服务端通常是多进程单 Tick 主循环模型。总 CPU 看起来没有 100%，但某个 BaseApp 或 CellApp 单核已满时，延迟仍会明显升高。

### 4. 内存

优先看：

- `memory.private`：进程真实私有提交内存，更适合比较优化前后。
- `memory.working_set`：当前驻留物理内存，受系统缓存和共享页影响。
- `memory.peak_working_set`：峰值工作集。

正式报告不要只用任务管理器的总内存比例下结论，应结合 `summary.json` 中各组件私有内存。

### 5. Tick 延迟

重点看 BaseApp / CellApp 的：

- P50
- P95
- P99
- P99.9
- Max

P50 代表常态成本，P95/P99 代表用户体验长尾，P99.9 更容易暴露偶发卡顿、Watcher 采样集中、AOI 扇出、Python Timer 峰值、IOCP 慢轮询等问题。

如果 P50 很低但 P99.9 很高，通常不是基础 CPU 不够，而是存在周期性突刺或排队。

### 6. KCP 指标

重点看：

- KCP 到期队列长度。
- 逾期通道数。
- 最大调度延迟。
- 实际重传。
- 快速重传。
- ACK 数量。
- 窗口阻塞。
- UDP 发送背压。
- BaseApp 外部 KCP queued segments。

如果 KCP 延迟很高但 CPU 总占用不高，要优先判断是否有单进程单核瓶颈、发送队列背压、KCP update 调度不及时，而不是只看整机 CPU。

### 7. AOI / Witness 指标

重点看 CellApp：

- `root/witness`
- `root/witness/scheduler`
- `root/witness/messages`
- `root/witness/queues`
- `root/witness/lod`
- `root/witness/backpressure`
- `root/spaces`
- `root/spaces/entities`
- `root/spaces/witnesses`
- `root/spaces/aoiRelations`

大量机器人随机移动时，如果出现“Avatar 罚站”或移动不连续，优先分析：

- CellApp 单核是否满。
- Witness 队列是否持续增长。
- AOI Enter/Leave 是否产生扇出风暴。
- Volatile 下发是否被高水位背压暂停。
- BaseApp KCP 队列是否已经堆积。

## 八、探针开关 A/B 测试

性能探针默认应关闭，压测发布时根据目标选择开启。

关闭探针：

```json
"performance_probes_enabled": false
```

开启探针：

```json
"performance_probes_enabled": true
```

A/B 对照建议：

1. 使用相同机器。
2. 使用相同 Bots 数。
3. 使用相同 BaseApp / CellApp 数。
4. 使用相同传输协议。
5. 每轮持续时间一致。
6. 对比 CPU、内存、Tick P99.9、Watcher request latency。

如果开启探针后 CPU、Tick P99.9 或控制面 latency 明显升高，需要减少 Watcher targets 或调大 `watcher_intervals`，不要把探针成本误当成服务端业务成本。

## 九、KCP / TCP 对照

Bots 与 LoginApp 的认证链路始终使用 TCP。`--bots-transport` 控制的是登录成功后的 BaseApp 游戏连接。

KCP 压测：

```powershell
--bots-transport kcp --bots-no-tcp-fallback
```

TCP 压测：

```powershell
--bots-transport tcp
```

正式 KCP 数据必须加 `--bots-no-tcp-fallback`。否则 KCP 建立失败的客户端可能回退 TCP，导致报告里混入协议样本，结论会失真。

## 十、常见问题排查

### 1. dbmgr 没报错，但其他组件找不到 dbmgr

优先检查：

1. MySQL 是否启动。
2. `kbengine.xml` 数据库账号、密码、库名是否正确。
3. dbmgr 是否已经进入 running 状态。
4. Machine 发现链路是否正常。
5. 端口是否被旧进程占用。

### 2. readiness 没达到

可能原因按优先级排序：

1. Bots 登录失败或角色流程未完成。
2. BaseApp KCP / TCP 游戏连接未建立完成。
3. CellApp Witness 未建立到预期数量。
4. 某些客户端超时、掉线或进入错误状态。
5. 服务端还没完全 ready，启动等待时间太短。
6. 数据库或脚本层存在错误。

验证方式：

- 查看 `summary.json` 的 `failure` 和 `quality.blockers`。
- 查看 `readiness.*` 样本。
- 查看 `logs\bots.*.log`。
- 查看 `logs\baseapp.*.log`、`logs\cellapp.*.log`。

### 3. 任务管理器 CPU 不高，但客户端延迟很高

这通常不是矛盾。多进程游戏服务端可能是某个 BaseApp 或 CellApp 单核已满，而整机还有其他核心空闲。

需要看：

- 单进程 CPU。
- Cell Tick P99/P99.9。
- KCP 调度延迟。
- Witness 队列。
- AOI 关系数量。

### 4. Bots 进程 CPU 或内存过高

建议：

- 增加 `--bots-processes` 分摊单进程压力。
- 正式压测不要加 `--bots-dev`。
- 日志级别保持 `warn`。
- 确认 Bots 没有把日志转发给 Logger。

### 5. 日志里出现 receive window overflow

常见原因：

- 客户端瞬时消息堆积。
- KCP 包解开后批量进入 Channel 接收窗口。
- BaseApp 当前 Tick 没有及时消费。

压测 overlay 支持调整：

- `external_receive_messages`
- `external_receive_bytes`

但这类配置只能缓解窗口告警，不能替代对 CPU、AOI、KCP 调度和消息处理链路的根因分析。

## 十二、给后续 AI 的执行提示

如果让另一个 AI 继续做压测，请按以下顺序执行：

1. 读取本文档。
2. 读取 `D:\KBELAB\kbengine\kbengine1x\kbe\src\tests\performance\README.md`。
3. 确认 `git status --short`，不要误改用户未提交内容。
4. 确认 MySQL 已启动。
5. 编译 Release。
6. 清理残留 KBEngine 进程。
7. 先跑 4000 Bots probes off。
8. 再跑 4000 Bots probes on。
9. 如果 4000 稳定，再跑 10000 Bots 正式 KCP。
10. 需要协议对照时，再跑 10000 Bots TCP。
11. 汇总 `summary.json` 和 `report.md`。
12. 如果失败，按“现象 → 日志 → 调用链 → 数据流 → 根因 → 修复”排查，不要直接调大超时或窗口掩盖问题。
